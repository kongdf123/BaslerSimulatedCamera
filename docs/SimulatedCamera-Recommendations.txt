The Three Blockers
Blocker 1: Driver registration is commented out
CameraDriverFactoryExtensions.RegisterCameraDrivers() (line 14–29):

csharp



factory.RegisterCameraDriver<BaslerCamera>();
//factory.RegisterCameraDriver<SimulatedCamera>();   // ← commented
//factory.RegisterCameraDriver<UsbCamera>();
Without this line, GetCameraDriver("SIM-CAM-01") returns null and CreateCameraInstance throws "未找到序列号对应的相机".

Blocker 2: Settings UI enumeration is hardcoded to Basler
VideoSettingsViewModel.Enumeration.cs calls BaslerDeviceEnumerator.TryEnumerateDevices() directly (line 315), not the factory's GetCameraDeviceList(). So even after registering SimulatedCamera, the dropdown only shows Basler devices. The "添加相机" button can never produce a SIM-CAM-xx row.

Blocker 3: Basler environment guard blocks all slots
CameraVideoDeviceService.TryApplyBaslerEnvironmentGuardBeforePreviewAsync() (line 104–124) probes the Basler runtime. On a machine without pylon/device, it returns false and writes a red-cross error to every configured slot — including simulated ones. So preview never starts.

Blocker 4 (minor): Health polling marks simulated as offline
VideoSettingsViewModel.HealthPoll.cs → BuildOnlineCameraPollResult uses TryEnumerateBaslerCameraOptions (line 389). A SIM-CAM-xx row would never match an online serial, so the status icon stays red.

Proposed Solution
A. Register the simulated driver (conditionally)
In CameraDriverFactoryExtensions.cs, uncomment the line — ideally gated by a debug/config flag so it doesn't pollute production:

csharp



factory.RegisterCameraDriver<BaslerCamera>();
#if DEBUG
factory.RegisterCameraDriver<SimulatedCamera>();
#endif
Or read from an IOptions/appsettings flag: factory.RegisterCameraDriver<SimulatedCamera>() only when EnableSimulatedCameras is true.

B. Make settings enumeration include simulated cameras
Two options:

Option B1 (cleaner): Change EnumerateBaslerCameraOptions to also pull from the factory. Inject ICameraDriverFactory (or ICameraSourceProvider) into VideoSettingsViewModel and merge:

csharp



// pseudo
var basler = BaslerDeviceEnumerator.TryEnumerateDevices(...);
var simulated = _cameraDriverFactory.GetCameraDeviceList()
    .Where(d => d.Driver == CameraDriver.Simulated);
// merge into options
Option B2 (simpler, no factory injection): Add a dedicated "添加模拟相机" button in VideoSettingsSection.xaml that directly creates device rows with SerialNumber = "SIM-CAM-01", Vendor = "Simulated", DisplayName = "Simulated Camera 1". This avoids touching the enumeration logic entirely and gives an explicit debug affordance.

C. Bypass the Basler environment guard for simulated cameras
In TryApplyBaslerEnvironmentGuardBeforePreviewAsync, split configured devices into Basler vs non-Basler. Run the Basler probe only for the Basler subset:

csharp



var baslerDevices = configuredDevices.Where(d =>
    !string.Equals(d.Vendor, "Simulated", StringComparison.OrdinalIgnoreCase)).ToList();

if (baslerDevices.Count == 0)
    return true;   // all simulated — proceed

// existing probe logic, but only apply errors to baslerDevices
D. Health polling: mark simulated cameras as online
In BuildOnlineCameraPollResult, after getting Basler online serials, also add simulated serials:

csharp



foreach (var row in rowsSnapshot)
    if (row.SerialNumber.StartsWith("SIM-CAM-", OrdinalIgnoreCase))
        onlineSerials.Add(row.SerialNumber);
Or skip the poll for simulated rows and call row.ApplyCameraStatus(Online, ...) directly.

Yes — it's absolutely possible, and the codebase already proves the pattern
The existing KW.DeviceLinkSimulatorTool already does exactly this for force plates: a separate console app listens on a TCP/UDP port, generates synthetic data, and KWinSprint connects to it as if it were a real device. The same approach works for cameras.

The key question is how much separation you want. There are two viable architectures.

Option A: In-process simulated camera (simplest, ~90% done)
The SimulatedCamera driver already exists and works entirely inside the KWinSprint process. After the wiring fixes I described (register driver, bypass Basler guard, add "add simulated camera" button), you get:

text



KWinSprint process
  ├─ SimulatedCamera (generates frames via Timer + CreateFramePixels)
  └─ UI sees "SIM-CAM-01", adds it, live preview works
No separate app. The simulator is just a driver. This is the fastest path to "live testing without a camera."

Option B: Separate simulator app + network camera driver (what you described)
This mirrors KW.DeviceLinkSimulatorTool exactly. The frame generation moves into a standalone app, and KWinSprint connects to it over the network.

text



┌─────────────────────────┐         TCP/WebSocket          ┌──────────────────────┐
│  CameraSimulatorApp.exe │  ◄──── discovery + frames ────► │     KWinSprint       │
│  (WPF or console)       │                                 │                      │
│  - generates frames     │                                 │  RemoteSimulatedCamera│
│  - configurable fps/res │                                 │  (CameraBase impl)   │
│  - inject glitches      │                                 │  - connects to app   │
└─────────────────────────┘                                 └──────────────────────┘
How it plugs into the existing architecture
The CameraBase abstraction is transport-agnostic. A new RemoteSimulatedCamera : CameraBase would implement the same contract as BaslerCamera/SimulatedCamera, but instead of talking to a physical device or a local timer, it talks to the simulator app over a socket:

CameraBase method	RemoteSimulatedCamera behavior
GetCameraDeviceList()	Connect to simulator's discovery endpoint, ask for its virtual camera list, return CameraDeviceInfo with Driver = Simulated
InitCamera(serial)	Parse SIM-CAM-01 → which virtual camera to talk to
OpenCamera()	Open TCP/WebSocket connection to simulator at the configured endpoint
StartCollect()	Send START command, spawn background reader loop that reads frame packets and calls RaiseFrameReceived()
StopCollect()	Send STOP, close reader loop
StartRecord(path)	Open local VideoWriter (record the frames we receive) — recording stays in KWinSprint
GetCameraParameterSettings()	Query simulator for current fps/resolution/exposure
The wire protocol (simple, custom)
The simulator app runs a TCP server (say port 5170). KWinSprint connects and exchanges simple text + binary frames:

text



KWinSprint → simulator:  "LIST"
simulator → KWinSprint:  JSON array of cameras:
                         [{"serial":"SIM-CAM-01","name":"Sim Cam 1","width":640,"height":480,"fps":30}]

KWinSprint → simulator:  "OPEN SIM-CAM-01"
simulator → KWinSprint:  "OK"

KWinSprint → simulator:  "START"
simulator → KWinSprint:  frame packets streaming:
                         [int32 width][int32 height][int32 pixelFormat][int32 byteCount][byte[] pixels]
                         [int32 width][int32 height][int32 pixelFormat][int32 byteCount][byte[] pixels]
                         ...

KWinSprint → simulator:  "STOP"
For bandwidth efficiency, the simulator could send JPEG-encoded frames instead of raw BGR (320×240 BGR = ~230KB/frame × 30fps = ~7MB/s — fine for localhost but JPEG would be much lighter).

Discovery
Two options:

Fixed endpoint (simplest): KWinSprint always probes 127.0.0.1:5170 when enumerating simulated cameras. If the simulator app is running, it responds; if not, no simulated cameras appear.
UDP broadcast (more like real GigE): simulator sends periodic beacons on a multicast/broadcast address; KWinSprint listens for them. This is closer to how Basler's GigE Vision discovery works, but overkill for localhost.

Recommendation
If your goal is just "debug the live test session without hardware" → use Option A. It's already built; you just need to flip the registration switch and bypass the guard. No network, no new app, no protocol design.

If you specifically want a separate simulator process (e.g., to test network latency, frame drops, or to run the simulator on a different machine) → Option B. The KW.DeviceLinkSimulatorTool proves this pattern works in this codebase, and the CameraBase contract makes the network driver straightforward.

You can also do both: keep the in-process SimulatedCamera for quick local debug, and add RemoteSimulatedCamera + a simulator app when you need out-of-process simulation.
